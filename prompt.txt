                                    7. LESS IS MORE — BUT DO NOT STRIP THE GAME
Apply a professional less-is-more refinement principle.
This does NOT mean:
                                       * remove personality
                                       * remove useful feedback
                                       * remove game mechanics
                                       * remove visual interest
                                       * remove satisfying interactions
                                       * remove educational value
                                       * flatten everything
                                       * make the game boring
                                       * reduce the number of useful features arbitrarily
Instead, it means:
trim unnecessary edges while protecting everything valuable.
Look for:
                                       * redundant controls
                                       * repeated information
                                       * visual clutter
                                       * excessive labels
                                       * unnecessary decoration
                                       * competing visual hierarchy
                                       * redundant animations
                                       * excessive transitions
                                       * unnecessary panels
                                       * confusing status indicators
                                       * repeated explanations
                                       * overly complicated flows
                                       * duplicated interaction patterns
                                       * excessive customization that does not improve gameplay
Refine rather than mutilate.
Use this principle:
Remove friction, not character.
Remove noise, not useful information.
Remove redundancy, not depth.
Simplify interactions, not meaningful gameplay.
Reduce cognitive load, not personality.
When removing or combining something, ask:
                                          1. Does it improve understanding?
                                          2. Does it improve speed?
                                          3. Does it improve usability?
                                          4. Does it improve visual hierarchy?
                                          5. Does it improve mobile interaction?
                                          6. Does it improve maintainability?
                                          7. Does it reduce cognitive load?
                                          8. Does it preserve or improve the game's identity?
Only make the change when the overall result is stronger.

                                                                        13. PROFESSIONAL RESEARCH PROTOCOL
Research must be deliberate.
Do not perform shallow searches simply to justify a predetermined decision.
For any important design, technical, accessibility, educational, or game-design question:
STEP A — Identify the question
Clearly determine what needs to be known.
Example:
"How should the game present multiple-choice answers on a narrow mobile screen?"
STEP B — Identify professional domains
Determine which professions would normally own the problem.
Possible domains include:
                                                                           * UX
                                                                           * UI
                                                                           * accessibility
                                                                           * front-end engineering
                                                                           * game design
                                                                           * educational design
                                                                           * cognitive psychology
                                                                           * information architecture
                                                                           * performance engineering
                                                                           * content design
STEP C — Research authoritative material
Prefer:
                                                                           * official standards
                                                                           * platform guidance
                                                                           * accessibility standards
                                                                           * established UX research
                                                                           * respected design systems
                                                                           * reputable engineering documentation
                                                                           * high-quality professional publications
                                                                           * credible research literature
Avoid building important decisions primarily around random blogs or unsupported opinions.
STEP D — Compare findings
Look for:
                                                                           * consensus
                                                                           * disagreement
                                                                           * context-specific recommendations
                                                                           * trade-offs
                                                                           * limitations
STEP E — Apply findings to the actual game
Ask:
"Does this principle improve THIS game?"
Do not force generic best practices into situations where they create worse UX.
STEP F — Implement only justified changes
Each meaningful change should have a clear reason.

                                                                                                   18. SCRIPT.JS CONTENT ARCHITECTURE
A major objective of this refinement is to establish a clean, scalable in-script content architecture.
There is no separate external content file.
There is NO separate JSON content file.
There is NO external content database for the game.
ALL game challenge/content data must live inside script.js.
The content section inside script.js must act as the game's content database, not as an unstructured dumping ground. Keep it clearly organized, ideally in one clearly identifiable data section near the top of the file, so a developer can immediately find and edit the game content.
The structure must be:
                                                                                                      * clear
                                                                                                      * readable
                                                                                                      * consistent
                                                                                                      * expandable
                                                                                                      * predictable
                                                                                                      * easy to edit
                                                                                                      * easy to duplicate
                                                                                                      * easy to extend
                                                                                                      * robust against malformed entries
                                                                                                      * appropriate for future versions
EXACT CONTENT LIMIT — FIVE PLAYTHROUGH EXAMPLES
For this version of the game, the content dataset in script.js MUST contain exactly 5 playable challenge examples.
These are not merely placeholder records. They are the complete example playthrough for the current version of the game.
Requirements:
                                                                                                      * Create exactly 5 playable challenge/content entries.
                                                                                                      * Do not create 6 or more challenges.
                                                                                                      * Do not generate additional hidden, backup, duplicate, random, or fallback challenges.
                                                                                                      * Do not expand the dataset beyond these 5 examples.
                                                                                                      * The game must be fully playable from beginning to end using these 5 examples.
                                                                                                      * The 5 examples should demonstrate the intended gameplay loop and provide a coherent sample progression.
                                                                                                      * The 5 examples may vary in type, difficulty, or situation where appropriate so that the player experiences the range of the existing game mechanics.
                                                                                                      * The game should normally progress through these 5 examples in a deliberate, valid playthrough rather than generating an unlimited challenge pool.
                                                                                                      * Do not interpret "future expansion" as permission to populate the current version with more than 5 examples.
                                                                                                      * The data architecture should still make it easy for a future developer to add more challenges later, but the current output MUST contain exactly 5.
The number 5 is an explicit content requirement and takes priority over any other instruction in this prompt that could be interpreted as requiring a larger challenge dataset.
The game engine must consume this in-script content data rather than keeping duplicate copies of challenge content throughout the codebase.

                                                                                                                                                                                                                                                                                                                                       61. CHANGE PRIORITIZATION
Not all improvements are equally important.
Prioritize in this order:
Priority 1 — Broken
Anything that prevents correct operation.
Priority 2 — Incorrect
Anything producing wrong logic, wrong content, wrong scoring, or wrong results.
Priority 3 — Confusing
Anything causing users to misunderstand the interface or rules.
Priority 4 — Poor mobile usability
Anything meaningfully harming touch interaction, readability, responsiveness, or mobile flow.
Priority 5 — Weak architecture
Anything making future maintenance or expansion unnecessarily difficult.
Priority 6 — Performance
Meaningful performance problems.
Priority 7 — Accessibility
Meaningful accessibility shortcomings.
Priority 8 — Visual polish
Spacing, typography, hierarchy, consistency, and refinement.
Priority 9 — Nice-to-have enhancements
Only after the fundamentals are excellent.
Do not waste time polishing a broken mechanic.
